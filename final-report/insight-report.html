1What was built

A Fruit-Ninja-style slicer that teaches Hong Kong's real recycling rules. Objects fly up from the bottom of the screen and you cut the ones that belong in the round's bin, leaving the rest to fall. It runs entirely in a browser with no install, and you can play it with your hand via the webcam, with your phone as a motion controller, or with a mouse.

What makes it distinctive

It teaches the thing people actually get wrong. The game's headline lesson is "wishcycling" — putting something in a recycling bin because you hope it counts. The greasy pizza box, the coffee cup, the bubble tea cup, the receipt and the face mask all look recyclable and are not. The fourth round of Sort mode inverts the rule so that only the non-recyclables are correct, which forces the player to know the difference rather than pattern-match on material.

The bins are the real Hong Kong ones. Categories follow the HK EPD GREEN@COMMUNITY scheme, so drink cartons and clean plastic bags are treated as recyclable — which surprises people — and the colour coding matches the bins on the street.

Your phone is a real motion controller. Scanning a QR code turns a phone into a sword: tilting aims, swinging cuts. It negotiates a direct WebRTC link to the laptop, and falls back to an internet relay only when it must.

The four modes

ModeHow it plays
SortFour rounds — Paper, Plastic, Metal & Glass, then the traps. Correct slice +15, wrong −12.
QuizA question appears and answers float up; slice the one you believe. 12 questions or 3 lives, with an explanation after every answer.
Bin ItNo blade. You move a bin along the bottom and catch what belongs in it.
VersusTwo players, 60 seconds, split screen, +1/−1. Needs two webcam hands or two phones.

Other features

  • Eight unlockable blade skins driven by an XP/level curve — cosmetic only, deliberately: a rarer blade never cuts better.
  • A local best score plus an optional Firestore leaderboard.
  • Per-material cut sounds: glass shatters, paper shreds, metal shears.
  • A six-lesson bilingual interactive tutorial that is played rather than read.

Six of the fifty painted item renders. The last two — bubble tea and the pizza box — are wishcycling traps.

2How it was built

Tech stack, and why

The whole game is plain HTML, CSS and JavaScript with no build step, no framework and no bundler. You open the folder, serve it, and it runs. That choice drove everything else, and it was the right one for a school project: there is nothing to install, nothing to compile, and a student can read any file and change it.

The single most valuable habit: measure, don't guess

Nearly every hard bug in this project was solved by measurement, and several "obvious" fixes were abandoned because the numbers said not to. The approved plan for the backdrop was to blur and darken it; measuring the file showed it arrived at a mean luminance of 3–8/255 in the sky and that the painted bins were already darker than mid-field, so it shipped untouched. The relay lag was diagnosed by measuring the broker at ~11 messages/second, not by tuning constants.

The audio went through four generations before it shipped

The working folder still holds every attempt, which makes this the best-documented asset in the project:

  1. Pure synthesis, generic — generate_slice_sounds.py produced 3 WAVs (slice-clean, slice-correct-arcade, slice-heavy-chop) from maths alone: noise, an envelope and a whoosh. No recordings.
  2. Pure synthesis, per category — generate_category_sounds.py produced 5 category-specific WAVs the same way.
  3. Real recordings gathered — 12 CC0 reference clips downloaded from Freesound.
  4. Edited down to 6, then 5 shipped — real clips layered, filtered and normalised.

Synthesised glass never sounded like glass. The shipped pack is real recordings, which is why the final files carry a SOURCES.md crediting each one.

4What went wrong

The project keeps an unusually honest record of its own failures. Every bug that reached the player is written up in CLAUDE.md as a rule with the reason attached — about 55 of them. That file is the single most valuable artefact here.

The expensive ones

1. A script-loading race that produced every "the game is broken" report

js/game.js started the render loop as soon as it loaded, but it calls a function defined in js/blades.js — the last of seven scripts. On a slow connection the first frame ran before that file arrived and threw.

Cost: it surfaced three separate times as three different-looking bugs — a frozen board (build 62), then a main-menu bounce where the round button both started the round and reloaded the page (build 63), then an error banner (build 66). It never reproduced on localhost, because all seven files arrive before the first frame is due.

Root cause: assuming load order is timing. The fix was to wait for DOMContentLoaded.

2. Versus was unplayable with two phones for weeks

Two players reported both blades lagging so badly the mode could not be played. The cause was a deliberate line of code: the host refused to answer a phone's WebRTC offer whenever two players were present, on the reasoning that "two phones can't share one connection". True — but the answer was to hold one connection each, not to give up.

So Versus ran entirely on the MQTT relay, which is ~205 ms round trip and capped near 11 messages/second per topic. Two phones publishing every 90 ms sent ~22 msg/s into an 11 msg/s pipe; roughly half was dropped, leaving each player about 5.5 irregular updates a second.

Root cause: a correct observation followed by the wrong conclusion, written down as a comment and then trusted for weeks.

3. A live API key committed to a public repo

The human spotted it, not the agent: "wait so there is the real API key in my github repo? ... I dont want anyone in the git can have my api key." It is a Firebase Web API key, which is designed to sit in client code and is protected by database rules rather than secrecy — but the surprise was real and the reasoning had to be explained after the fact rather than before.

Root cause: a security-relevant default was applied without being explained at the time.

4. Bin It had to be redesigned from scratch

"The design of the bin it mode is not make sense. So hard to play." The original version had you slicing items to nudge them sideways into bins. It failed for three measurable reasons: the bin highlight ignored momentum and was wrong 46% of the time, items coasted 1.13 bin widths after you stopped pushing, and the push saturated so every phone swing maxed out.

Cost: an entire mode rewritten. Root cause: a control scheme that was never playtested before it was built out.

5. Phone control took many rounds of tuning

The chat history is full of it: "the moving speed of the blade should also be increased", then "the moving speed is too fast", then "the control is still not smooth and make sense. user is hard to control". Along the way the accelerometer was tried and abandoned (it measures force, not position), and a sign error on yaw inverted the aim in one build.

Root cause: motion control cannot be reasoned about from a desk — it needs a person holding a phone, and every round trip cost a deploy.

Smaller ones worth knowing

  • A silent asset typo. A tutorial step asked for an item called canAlu, which does not exist — the real key is canTall. The lookup failed silently, no item spawned, and the lesson hung forever looking exactly like a player who had not acted yet.
  • A GPU memory leak. Every item allocated a material that was never disposed; a few hundred accumulated per game and kept accumulating across replays.
  • Items launched off the top of the screen on short landscape phones, invisible and unslicable, because a floor was added to the launch height without keeping a ceiling.
  • A screen reader was told the opposite of what was drawn — aria-pressed never moved with the selected menu tile.
  • The menu showed the last click, not the actual state, so after a round it could highlight "Sort" while the header read "Versus selected".
  • An error handler made things worse than the error. It attached a reload to a button that already had a listener, so once any fault had fired, "Start round" both started the round and reloaded the page.

Four things that went unusually well

  1. Writing every bug down as a rule, with the reason. CLAUDE.md grew to ~55 invariants, each stating what broke, why, and what must never be done again. This is why the same bug rarely appeared twice across 117 commits, and it is the most transferable habit in the whole project.
  2. Tests that describe player-visible failures, not functions. 14 harnesses and 362 assertions, with names like "the blade never leaves the playfield" and "a phone genuinely put down still goes quiet". They read the real source files, so they test shipped code rather than a copy.
  3. Fallbacks for every asset. The painted item renders fall back to canvas drawings; the backdrop falls back to a gradient; a missing sound leaves the game playable. Each fallback was verified by actually deleting the file and looking. A blocked school network cannot break this game.
  4. Measuring instead of guessing. Backdrop luminance, JPEG PSNR, broker throughput, audio RMS, webcam dropout rates — decisions were made from numbers, and several planned "fixes" were correctly abandoned when the numbers disagreed.

Workflows that deserve to become agent skills

Skill 1 — Integrate an art pack safely

Inputs: a folder of images, plus the game's existing item/entity list.

  1. Validate coverage against the game's own data first: every key present, no extras, no duplicates. Stop and report if it does not match.
  2. Derive file paths from the existing keys so there is no manifest to drift.
  3. Preload once at boot and cache by key; never allocate per spawn.
  4. Keep the old artwork as a fallback and verify it by deleting an asset and looking.
  5. Update every path that draws the art, not just the obvious one.
  6. Write a harness covering coverage, format, caching, fallback and no per-spawn fetches.

Output: integrated art, a fallback that works, and a test that fails if the pack and the roster ever disagree.

Skill 2 — Add a game mode

Inputs: mode name, win/lose condition, scoring rule.

  1. Create a state object, a launcher, an update, a hit test, a draw and a game-over.
  2. Register the mode in GMODE, the loop, the menu tiles and show().
  3. Declare which controllers it supports — and hide it for controllers it cannot use.
  4. Add a pause path and a "how to play" reference entry.
  5. Add a fairness harness: can the mode be won, and can it be lost unfairly?

Output: a mode wired into every shared system, with tests.

Skill 3 — Diagnose input lag before tuning it

Inputs: a report that controls feel laggy.

  1. Measure the transport first: actual message rate delivered, and round-trip latency.
  2. Compare against the theoretical rate. If they differ, the problem is the pipe, not the tuning.
  3. Check whether a faster path exists and is actually being used.
  4. Only then touch smoothing or prediction constants.

Output: a root cause with numbers. This project lost weeks by skipping straight to step 4.

Skill 4 — Ship an image asset

Inputs: a supplied image.

  1. Measure it before editing — luminance, contrast in the regions that matter.
  2. Re-encode, then verify the re-encode (PSNR, max error, banding in gradients).
  3. Declare width/height in markup; add a CSS fallback underneath.
  4. Add the file size to a budget test.

Output: a small, verified asset that degrades safely.

What a starter template should have contained on day one

  1. A boot sequence that waits for every script — the single most expensive bug here, and a template solves it permanently.
  2. A test harness pattern and a npm test that syntax-checks first. A parse error once passed the entire suite because the harnesses read files as text.
  3. A CLAUDE.md with an empty "Invariants — these were each a shipped bug" section. The habit matters more than the content.
  4. Asset loading with a fallback baked in, plus a size budget test.
  5. A resolution budget by pixel count, not a fixed ratio — large displays otherwise pay more than double a laptop's cost per frame.
  6. A screen router, pause overlay and error banner with its own buttons, never borrowing game UI.
  7. The phone-controller stack as a working starting point. This was days of work and is almost entirely game-agnostic.
  8. A note that CSS features like color-mix() and oklch() are banned — on a school machine a silent colour failure is invisible.
